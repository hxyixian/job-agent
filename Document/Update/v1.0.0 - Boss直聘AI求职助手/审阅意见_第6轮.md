## 3. 问题与建议

### R6-1.（高）配置校验缺口

我用 `Config.model_validate` 构造了下列 8 组非法配置，**全部被接受**：

| 构造的配置 | 后果 |
|------------|------|
| `console.host: 0.0.0.0` | 控制台监听所有网卡，局域网内的任何设备都能访问；违反 S1 加固第 1 项"仅监听 127.0.0.1" |
| `delivery.min_interval_s.detail: -5` | H2 的节奏下限失效 |
| `delivery.action_delay_range_s: [0, 0]` | 拟人延时被取消 |
| `delivery.hourly_limit: -1` | 限额的语义变得不确定 |
| `ai.min_score: 150` | 永远没有职位能投递，而且不会报错 |
| `notify.feishu.levels: [low]` | 高级告警不再推送到飞书；违反 FR7.2"高级告警邮件 + 飞书必推" |
| `site.browser_strategy: typo` | 拼写错误要到运行时才暴露 |
| `messaging.resume_auto_send_limit_per_conv: 5` | 违反需求中"每会话最多自动投递 1 次"的硬性规则 |

**建议**：

- **`console.host`**：限定为 `Literal["127.0.0.1"]`（或校验必须是回环地址）。这项属于安全约束，不应该开放配置。
- **数值字段**：全部加上 `ge` / `le` 约束：
  - 各类限额 ≥ 0；`min_score` 在 0–100；`temperature` 在 0–2；
  - `RangePair` 两个值都 ≥ 0；`resume_auto_send_limit_per_conv` 在 0–1。
- **安全相关参数**（`min_interval_s`、`action_delay_range_s`、浏览上限）：
  - 硬下限设为 ≥ 1，用来拦截明显错误的值；
  - 低于已验证的默认值时（比如最小间隔低于 30 秒），启动时记一条 WARNING，并在控制台配置页提示"低于实测验证过的节奏"。

  这样既保留调参的余地，又不会被悄悄关掉保护。
- **枚举字段**：`adapter`、`browser_strategy`、`channel` 改用 `Literal`。
- **飞书推送级别**：`notify.feishu.levels` 加校验，必须包含 `high`。
- 每条规则补一个拒绝用例。

### R6-2.（中）路径相对于当前工作目录

- 现状：`DEFAULT_CONFIG_PATH = Path("config.yaml")`、`data.db_path = data/agent.db`、`setup_logging(logs_dir="logs")`，都是相对于当前工作目录的。
- **风险**：从其他目录启动（比如以后写的启动脚本、开机自启、或在 IDE 里换了工作目录），程序会：
  - 读不到配置，静默回落到默认值；
  - **新建一个空数据库**，去重名单和投递记录都不在里面，导致重复投递。

  单实例锁是全局的，只能防止两个实例同时运行，防不了先后从不同目录运行。
- **建议**：
  - 确定一个固定的应用根目录（比如项目根目录，或通过环境变量 `JOB_AGENT_HOME` 指定），所有相对路径都基于它解析；
  - 启动横幅和日志里打印配置、数据库、日志三者的**绝对路径**；
  - 补一个测试：在另一个工作目录启动时，解析出的路径不变。

### R6-3.（中）在库层为关键约束兜底，并补上 F1 的存储位置

0001 迁移还没有在任何真实数据库上执行过，建议**直接修改 0001**：

1. **"绝不重投"的兜底**：

   ```sql
   CREATE UNIQUE INDEX uq_applications_job_real ON applications (job_id) WHERE dry_run = 0;
   ```

   即使应用层逻辑出错，同一个岗位也不可能产生第二条正式投递记录（FR8.5）。
2. **每种模板、简历只能有一个"当前版本"**：

   ```sql
   CREATE UNIQUE INDEX uq_greeting_current ON greeting_templates (kind) WHERE is_current = 1;
   CREATE UNIQUE INDEX uq_resume_current ON resume_snapshots (is_current) WHERE is_current = 1;
   ```

3. **F1 的同步确认存储**：开发文档 S5b 要求"已同步到平台"的确认与模板内容哈希绑定，但设计 §6 和 0001 都没有对应字段。建议给 `greeting_templates` 加两列：
   - `platform_synced_hash TEXT`：确认时的模板内容哈希；
   - `platform_synced_at TEXT`：确认时间。

   判定规则：`platform_synced_hash == 当前内容哈希` 即视为已同步。同步修改设计 §6。
4. 可选：给 `send_intents` 加 `CHECK ((state = 'skipped_dryrun') = (dry_run = 1))`，防止试运行记录和正式记录混淆。

每项补一个约束生效的测试（插入第二条正式投递记录应当失败）。

### R6-4.（中）时间戳时区约定要写进契约

- 现状：所有时间戳都以 UTC 存储（`...Z`）。这个设计本身是好的，字典序就是时间序。
- **问题**：每日限额、放量期的"有效运行日"、每日摘要，都是按 **Asia/Shanghai 自然日**计算的（B18）。如果 S2b 直接用 UTC 日期来划分"一天"，每天的分界线就落在北京时间 08:00。目前运行时段是 10:00–16:00，暂时不会出错，但只要你把时段调到早于 08:00，一天的限额就会被拆到两个"天"里。
- **建议**：在设计 §5.5 I1 里写明换算规则："日窗口起点 = 北京时间当天 00:00 换算成 UTC 字符串，再和 `created_at` 比较"。提供一个公共函数 `day_start_utc(now)`，供 S2b / S2c / S2d 共用，并补一个测试：北京时间 07:59 和 08:01 属于同一天。

### R6-5.（中低）入口还没有接入日志模块和单实例锁

- `__main__.py` 用的仍是 `logging.basicConfig`，日志模块和单实例锁只留了注释占位，所以：
  - 入口运行时**不写日志文件，也不打码**；
  - 两个实例可以同时启动。
- 按开发文档，入口的最终装配归 S5d，所以不算不合格。但这两项接入只要几行代码，现在接上，Stage 2–4 开发和调试期间就能一直使用真实的日志与打码，避免两套日志路径并存。
- 另外 `__main__` 的覆盖率是 0%。建议补一个冒烟测试：在临时目录调用 `main()`，断言返回 0，并生成了 `logs/app.log`。

### R6-6.（低）`Database` 的锁覆盖范围

- `execute()` 返回游标，调用方取数据的时候已经出了锁的范围。建议改为返回 `rowcount` / `lastrowid`；需要取数据的一律走 `query` / `query_one`。
- `connection` 属性的注释写着"仍受本类锁保护"，但这个属性本身不加锁。改注释，或者去掉这个属性。

### R6-7.（低）代码格式

- `ruff format --check` 显示 `db.py` 等 3 个文件未格式化。建议运行一次 `ruff format`，并把 `ruff format --check` 加进 A-BUILD-2，避免后续 SubAgent 之间的格式差异造成 diff 噪音。

### R6-8.（低）标准输出重定向时中文会乱码

- 用 Git Bash 管道运行入口时，横幅和日志里的中文全部乱码：标准输出被重定向时，Python 在 Windows 上按 GBK 输出。直接在控制台窗口里运行不受影响，但如果以后用启动脚本把输出重定向到文件，就会出现乱码。
- **建议**：入口开头执行 `sys.stdout.reconfigure(encoding="utf-8")`（stderr 同理），或者在启动说明里设置 `PYTHONUTF8=1`。
