### A2. 单会话自动发送上限（默认 2）被附件简历和被动招呼挤占（需用户决策）

- **现状**：FR6.3 规定上限包含招呼语；FR3.7 的被动招呼语和附件简历都计入；FR3.8 的附件简历也计入。
- **按默认值推演的后果**：
  1. 被动招呼会话：一发出就达到上限，马上触发中级告警"会话达自动上限"，之后的消息全部转人工；
  2. 主动投递且 FR3.8 开启：招呼语 1 次 + 简历 1 次 = 2 次，之后连一条低风险消息都不能自动回复；
  3. 主动投递且 FR3.8 关闭：招呼语之后只剩 1 次低风险自动回复；
  4. FR6.3 允许把上限配成 0，但招呼语也计入上限，配 0 就无法投递，规则自相矛盾。
- **方案**：
  - **a（推荐）**：附件简历不计入自动回复上限，另限每个会话最多自动发送 1 次；上限配置做下限校验，最小为 1（留给招呼语）。
  - b：计数口径不变，默认上限改为 3。
  - c：维持现状，用户知悉以上后果。
- 这是产品行为偏好，需要用户拍板。

### A3. 缺少"试运行（只读演练）模式"和首次真实投递的上线策略（需用户决策，属于需求增补）

- **现状**：§6 规定"v1 完成后不允许直接上线实测"，TEST3 只覆盖登录态检测、搜索和读取会话。从"验收通过"到"第一次真实投递"之间没有任何过渡安排。TEST2 的 50 个真实 JD 夹具和 L1 阈值校准也没写数据从哪里来（这需要一个已经能读真实页面的工具）。
- **建议增补的需求**：
  - **试运行模式** `dry_run`（首次安装时默认开启）：真实执行搜索、抓取 JD、AI 评估、轮询、消息分类和草拟回复，但所有 `send_*` 操作都改为记录"拟发送"。控制台可以查看"正式运行时会发出什么"。
  - **首次实投逐步放量**：试运行通过后，前 N 天使用较低的上限（例如每日 10 次，低风险自动回复关闭，全部进待发箱），由用户手动调高。
  - 50 个 JD 夹具和 L1 校准数据直接取自试运行记录。
- **好处**：不发任何消息就能验证真实页面兼容性、筛选质量和评估质量，账号风险最低。

### A4. 测试夹具和验收证据存在哪里、怎么脱敏（需用户决策）

- **现状**：仓库已配置远端 `origin = https://github.com/hxyixian/job-agent.git`。TEST4 要求保留 JD 夹具和 persona 配置，但没写存放位置。TEST3/TEST5 的证据（截图、日志）会包含 HR 姓名、公司、聊天内容和账号信息。按规范第 8 节，验收报告放在 `Document/Update/...` 下，提交后会一起公开。
- **建议**：
  - 原始夹具和原始证据统一放在 `private/` 的子目录里（该目录已被忽略）；
  - 入库的只能是脱敏版本：去掉 HR 姓名、头像、ID、链接，以及聊天原文中的个人信息；
  - 验收报告只引用脱敏后的证据摘要，加上本地私有路径。
- **需用户决定**：脱敏后的 JD 夹具能否放进公开仓库。如果不能，新克隆的环境就跑不了 TEST2 回归。

### A5. 匹配评估的投递判定规则，以及 L1 遗留项如何关闭（需用户确认）

- **现状**：FR4.2 只规定 `verdict == skip` 时不投，没说 `neutral` 投不投；"阈值可配置"里的阈值和 verdict 怎么组合也没定义。v2-Q10 曾写"约对应 score < 60"，现在默认值表里是"未定"。规范 3.5 要求 Version 收尾时问题清单没有未关闭项，所以 L1 必须有明确的关闭路径。
- **建议**：
  - **判定规则**：`verdict != skip AND score >= min_score`。score 和 verdict 矛盾时（例如 90 分但 verdict 是 skip），按更保守的一方处理。`neutral` 投不投做成开关，**请用户确认默认值**：推荐"允许"，保证投递量；选"不允许"则更符合"宁缺毋滥"。
  - **L1**：v1 先用临时默认值 `min_score = 60` 运行。关闭条件写进验收文档：用户把 50 个 JD 逐条标成"愿意投 / 不愿投"，再把评估分数分布和人工标注对照着选定阈值，结果记入验收报告后关闭 L1。**需用户确认愿意做一次约 50 条的标注。**

## 2. B 级：阶段二设计必须给出明确契约

建议 MainAgent 把以下各条写进阶段二 `问题清单.md` 的自决区。置信度不到 90% 但不涉及路线分歧的，按规范 6.2 同样自决，并注明"待用户检查"。

### B0. 阶段二开头：对 Boss直聘真实页面做一次只读勘察

- **理由**：没看过真实页面就设计 ZhipinAdapter 的流程和选择器，违反"零猜测"原则。下面这些事实只能靠勘察确认（根据公开的使用经验大概率存在，但需核实）：
  1. 点击"立即沟通"时，平台会不会自动发送账号里预设的招呼语？如果会，就和 FR5 的固定模板重复发送，也会影响 FR6.3 的计数；
  2. HR 索要简历时，是不是以带"同意/拒绝"按钮的系统卡片出现？这影响 FR3.8 的识别和 B1 的路由；
  3. 平台每日主动沟通次数到上限时，提示长什么样（见 B6）；
  4. 站内有多份附件简历时，发送时怎么选（影响 `send_resume`）；
  5. 会话页能不能拿到关联岗位的 ID（FR3.7 的前提）；
  6. 系统消息（已读、交换微信成功等）以什么形式出现。
- **建议**：用户扫码登录后，由 Agent 只读访问页面，产出脱敏后的页面结构记录（去掉个人信息的 DOM 片段，存 `private/`），设计文档只引用结论。

### B1. 消息路由优先级：平台结构化卡片、多模态消息、正向回应三者冲突

- FR6.1 把"职位卡片/附件"归为多模态，一律进待发箱。如果 FR3.8 的"索要简历"是以系统卡片出现的，这两条规则就冲突了。
- **建议的路由顺序**（从高到低）：
  1. 系统通知（已读、对方已查看简历等）→ 不回复，只用于 FR8.2 的状态推断；
  2. 交换微信/电话的请求卡片 → **永远不自动处理**，进待发箱并发中级告警（隐私底线）；
  3. 索要简历的卡片或文字 → 按 FR3.8 的开关走；
  4. 面试邀请卡片 → 归为关键消息，发中级告警"面试邀约"；
  5. 图片/语音/文件 → 多模态路径；
  6. 普通文本 → 交给 AI 分类。
- 还要写明两点：一条消息有多个意图时按风险最高的处理；分类调用失败或结果解析失败时按"关键"处理（FR9.3 只规定了回复生成失败怎么降级）。

### B2. 增加"无需回复"类别

- "好的""收到"、纯表情这类消息，现在要么归为"低风险 → 自动回复"（FR6.1 L87），白白消耗 2 次额度（见 A2）；要么归为多模态进待发箱，产生没意义的条目，1 小时后还会触发高级告警（FR6.4）。
- **建议**：新增"无需回复"类：标记为已处理，不发送、不计数、不告警。

### B3. 首次运行建基线，并检测用户手动接管的会话

- FR3.7 的触发条件是"HR 主动发起"。但软件安装前就有的会话，以及用户自己在手机 App 上发起的会话，在库里同样没有投递记录，会被误判成 HR 主动来询，从而自动发出被动招呼语和简历。
- **建议**：
  - 第一次运行时给会话列表拍一次基线快照。基线里的会话一律当作人工会话，不参与自动化。基线会话的公司是否导入去重名单由配置决定（建议默认导入）；
  - 会话中出现不是本软件发出的我方消息（用户在 App 或网页上手动回复了），这个会话就自动转人工，不再自动发送。

### B4. 发送动作的状态机与崩溃一致性（这是 FR8.5"绝不重投"能成立的前提）

- **风险**：如果在"已点击发送"之后、"写入数据库"之前崩溃，重启后库里没有记录，就会再投一次。
- **建议**：
  - 发送前先在库里记下意图（`pending`），执行后改为 `sent` 或 `failed`；
  - 重启时把残留的 `pending` 改为 `unknown`，只做对账（去查会话列表），**禁止自动重发**。这和 NFR2"不静默重试投递动作"一致；
  - 小时和每日计数都从数据库推算，重启不清零；"每日"按 Asia/Shanghai 时区的自然日计算。

### B5. 浏览器只能由一个执行者操作

- 投递循环、消息轮询、登录检测，以及从控制台发起的人工发送，用的是同一个持久化浏览器上下文。Playwright 的 API 不是线程安全的。
- **设计里要写清楚**：
  - 所有站点操作都通过一个执行者串行完成（队列 + 优先级：登录/风控检测 > 回复 > 投递）；
  - 8-20 秒随机延时是否也用于回复操作；
  - 用户手动关掉浏览器窗口或浏览器崩溃时，进入暂停状态并告警，用户可以从控制台重新拉起浏览器；
  - 加单实例锁，防止软件被启动两次、两个进程同时占用同一个 profile。

### B6. 平台侧的次数上限

- 需求只定义了我方的三级频率控制，没考虑平台提示"今日沟通次数已达上限"这类情况。如果把它当成"适配器疑似失效"，会误发高级告警；如果忽略它，程序会一直重试。
- **建议**：新增一种信号类型。收到后当天停止投递，消息处理照常，发中级或低级通知。这种情况要和"风控暂停""适配器失效"区分开。

### B7. "适配器疑似失效"的判定条件必须能测试

- FR7.2 和 R3 只给了名称，没给判定条件。**建议定义**：关键元素连续 N 次（默认 3，可配置）定位失败，或关键页面结构校验失败，就暂停全部任务并发高级告警。

### B8. 补全 SiteAdapter 契约（FR10.1）

- **缺少"会话 → 关联岗位"的查询**，FR3.7 无法实现。建议新增 `get_conversation_job(conv_id) -> JobRef | None`，或者让 Conversation 模型直接带上岗位引用。
- `ensure_login_state()` 这个名字听起来会去"确保"登录，和 FR1.2"绝不执行任何登录操作"冲突。建议改名为 `check_login_state() -> LoginState`。
- 设计文档还要给出：
  - 数据模型：Job / JobDetail / Conversation / Message。Message 要包含发送方、类型、是否系统消息、时间、平台消息 ID；
  - 错误分类：登录失效 / 风控 / 适配器失效 / 平台限额 / 可重试的临时错误，以及调用方分别怎么处理；
  - 接口用同步还是异步；
  - `send_resume` 在有多份附件简历时选哪份（做成配置）。
- MockSiteAdapter 和 ZhipinAdapter 实现同一套契约，并且能通过注册机制在正式入口按配置切换（TEST5 依赖这一点）。

### B9. 筛选规则的语义和执行顺序

- **薪资匹配**：按区间重叠还是区间包含？"面议""元/天""·14薪"怎么处理？TEST1 需要精确的规则才能写用例。
- **执行顺序建议**：搜索 → 列表级规则（城市、薪资、去重、按公司名排除）→ 打开 JD → 详情级规则（排除关键词、经验要求）→ AI 评估 → 发送。先用列表信息过滤，可以少打开页面，也减少被风控注意到的机会。
- 同一个职位的评估结果按岗位 ID 缓存，不重复评估。
- **去重键**：优先用平台的公司/品牌 ID，规范化后的公司名作后备（品牌名和工商注册全称经常不一样）。
- 已被拉黑公司的 HR 主动来询时，是否仍走被动招呼要写明（建议允许，但照常经过 AI 评估）。

### B10. 待发箱的规则

- 用户在待发箱里确认发出的消息，算不算"自动发送"次数（建议不算）。
- 会话达到上限转人工后，AI 是否还继续为新消息写草稿。v2-Q9 写的是"转入待发箱全人工模式"，FR6.3 没有明说。
- **草稿过期**：用户确认发送时，如果这个会话在草稿写好之后又来了新消息，要提示用户重新确认或重新生成。
- **超时提醒**：每轮检查把所有超时条目合并成一条高级告警，避免多条同时超时时一条一条地发邮件。这是合并，不是冷却，和 P3 的决策不冲突。
- 运行时段之外到期的超时怎么处理，和 B11 一起定义。

### B11. 免打扰时段与各级告警的关系

- FR7.4 没说免打扰期间的高级告警是照常推送、延后推送还是丢弃。**建议**：高级告警不受免打扰限制（可配置）；中、低级告警延后到免打扰结束后合并推送；通知中心始终实时记录。
- FR7.3：如果消息轮询时段单独配置，每日摘要跟着哪个时段结束（建议跟投递时段）？时段结束时软件没在运行，要不要补发（建议不补发，下次启动时在总览页显示）？

### B12. AI 输出的安全护栏（防信息泄露和提示注入）

- HR 消息和 JD 都是不可信的输入，会被放进提示词；低风险消息自动发送时没有人把关。FR6.2 和 NFR1 要求的"不编造、不承诺"现在只能靠提示词约束，没法验收。
- **建议**：
  - 自动发送前做规则检查。内容里有手机号、邮箱、微信号、证件号、薪资数字、具体日期时间的承诺，或者超过长度上限，就降级进待发箱；

## 3. 安全与隐私

### S1. 本地控制台可被网页跨站调用（R4 的风险描述不完整，按 B 级处理）

- R4 写的是"同机程序可访问 API，风险低"。但更主要的入口是：用户日常浏览器里打开的任何网页，都能向 `localhost:8000` 发起跨站请求（CSRF）；配合 DNS 重绑定，还能读到返回内容。可能的后果：
  - 把 AI 的 `base_url` 改成攻击者的地址，简历全文和 API Key 就被发了出去；
  - 让软件给 HR 发消息。
- **建议**（不加登录鉴权，不改变 R4 的决策）：
  - 只监听 127.0.0.1；
  - 校验 Host 头，只接受 `localhost` 和 `127.0.0.1`；
  - 会改变状态的接口要求 JSON 请求体加自定义请求头（或 CSRF token）；
  - GET 请求不产生任何副作用；
  - 接口返回的 API Key、Webhook 密钥、SMTP 授权码一律打码。
- 同时修改 R4 的风险描述。

### S2. 公开仓库里的个人信息（C 级，由用户决定）

- 问题清单 L225 写着简历原文件名，里面有真实姓名；需求文档 §1 写了求职意向和期望薪资。已确认简历 PDF 从未进入 git 历史。文档里的这些信息要不要脱敏，由用户决定。

### S3. 日志与数据保留（C 级）

- 日志和 SQLite 里会有 HR 的聊天内容。建议日志轮转和保留天数可配置；日志里不输出 API Key 和完整简历。

## 4. 测试与验收能否执行

### T1. TEST2 没有通过/失败标准

- AI 扮演的 persona 每次输出都不一样，同一个用例可能这次通过、下次失败。
- **建议分两层**：
  - **脚本回放（结果固定）**：persona 的消息序列写死，检查路由、计数和状态变化，可以进回归；
  - **AI 自由对话（探索用）**：只统计指标。
- **安全底线必须 100% 满足，违反任何一条就判失败**：
  - 关键消息、多模态消息、交换联系方式的请求，被自动发送 0 条；
  - 会话上限被突破 0 次；
  - 自动发出的内容中出现联系方式或承诺 0 次；
  - 已投过的公司被重复投递 0 次。
- 低风险自动回复命中率这类体验指标只记录、不设门槛（或者由用户给出门槛）。

### T2. TEST3 是需要用户协助的验收项

- TEST3 需要用户扫码登录、使用真实账号，验收 Agent 自己完成不了。规范第 4、5 节要求无法执行的验收项不能默认通过，所以验收文档要写明：
  - 谁来执行（用户 + Agent）和操作步骤；
  - 操作频率仍受三级频率控制限制；
  - 证据要脱敏（见 A4）；
  - 没执行时记为"阻塞"，并写进问题清单置顶区。
- 如果采纳 A3，TEST3 可以扩展为"完整试运行一轮"。

### T3. TEST5 模拟环境的要求

- 正式入口要能通过配置切换到 MockSiteAdapter（见 B8）。
- 通知由本地的假 Webhook 接收端和本地 SMTP 收件端接收并做检查，不往真实的飞书和邮箱推送（可以另加一次真实推送的冒烟测试）。

### T4. 建议验收文档必须包含的关键用例（第 4 轮验收会逐条执行）

1. 在"已发送、还没写库"的时刻注入崩溃 → 重启后不重发，记录状态为 `unknown`，等待对账；
2. 循环进行中登录失效 → 当前操作结束后全部任务停止；发出高级告警、显示横幅、写日志；全程没有任何登录动作；
3. 出现风控页 → 暂停，用户手动恢复之前不再有任何站点操作；
4. 滑动窗口小时上限和每日上限在重启前后连续计数；
5. 会话计数口径（按 A2 的决策）正确，达到上限后转人工；
6. 去重：永久拉黑和冷却 N 天两种模式；
7. 运行时段边界和工作日判断（如周五 16:00、周六）；
8. 免打扰期间各级告警的行为（按 B11）；
9. FR3.7 和 FR3.8 开、关两种状态下的行为，以及模板没定稿时的行为；
10. AI 超时或返回非法 JSON → 评估按跳过处理，回复转待发箱；
11. 提示注入测试夹具 → 不泄露信息、不自动发送。

- 建议给 `core/`、`ai/`、`notify/` 设置行覆盖率门槛（如 ≥ 80%），作为客观的验收指标。

### T5. ZhipinAdapter 的离线回归测试
