## v1（初次梳理，2026-11-05）

### 置顶区（待用户确认，阶段阻塞）

#### Q1. 软件交互形态：本地 Web 控制台 / CLI / 桌面 GUI
- 问题描述：需求表述为"AI Agent 软件"，未明确交互形态。CLI、本地 Web 控制台、桌面 GUI 三条路线对整体架构（是否需要前端页面、进程模型、配置入口）影响重大，选错返工成本高。
- 建议方案：**本地 Web 控制台**（FastAPI 后端 + 浏览器访问 `http://localhost:端口`）。理由：a) 与"浏览器自动化"场景天然配合，软件本身就在驱动一个浏览器；b) 配置 AI、审核 AI 草拟的回复、查看投递记录，都是典型的表单+列表交互，Web 页面开发效率最高；c) 用户技能栈（简历：FastAPI/Pydantic）与该方案完全匹配，后续维护成本低。
- 备选方案：
  - B1：纯 CLI（终端菜单 + 命令行参数）。最轻量，但审核 AI 回复、编辑消息在终端里体验差，自动回复的"人工确认"流程几乎不可用。
  - B2：桌面 GUI（PySide6）。独立窗口应用观感最好，但开发量约为 Web 控制台的 2 倍以上，且对核心价值（自动化）无增量。
- 风险预警：Web 控制台需要打开浏览器访问 localhost 使用，不是独立窗口程序；若用户预期是"双击打开的桌面软件"，需选 B2 或后续打包 Electron/WebView 壳。
- 置信度：75%
- 归入置顶原因：三条路线架构差异大，属重大技术路线分歧，需用户拍板。

#### Q2. 浏览器自动化技术路线：Playwright / DrissionPage
- 问题描述：Boss直聘反自动化检测较强。需求说明"用户自行登录网站"，即方案为：持久化浏览器会话（user-data-dir），用户首次手动扫码登录，Agent 复用已登录会话操作。驱动浏览器的库需要二选一。
- 建议方案：**Playwright（Python 版）+ 持久化用户数据目录**。理由：a) 微软官方长期维护，API 完整（选择器、等待、网络拦截、多页面管理）；b) `launch_persistent_context` 是一等公民，"手动登录一次、之后复用会话"是成熟用法；c) 文档与社区规模大，SubAgent 并行开发时资料充足。
- 备选方案：
  - B1：DrissionPage。对国内站点反检测口碑好（更接近真实浏览器指纹），但社区规模小、API 稳定性和文档不如 Playwright，SubAgent 开发风险高。
- 风险预警：**无论哪种方案，自动投递/自动回复都属于平台敏感行为，可能触发限流、验证码甚至封号**。缓解措施：默认保守频率（操作间随机延时）、每日上限、异常检测自动暂停。风险无法完全消除，需用户知情接受（见 Q3）。
- 置信度：80%
- 归入置顶原因：核心执行层选型，切换成本极高；且附带账号风险决策。

#### Q3. 账号风险接受度与自动化程度底线
- 问题描述：Boss直聘用户协议限制自动化操作。自动投递/自动回复存在账号被限流/封禁的风险，无法由 Agent 规避，必须由用户决策自动化程度的底线。
- 建议方案：**知情接受风险，启用保守频率控制的全自动模式**（操作间 3-8 秒随机延时、每日投递上限默认 30、检测到验证码/风控页面立即暂停并通知用户人工处理）。
- 备选方案：
  - B1：半自动模式——Agent 只做"发现职位 + AI 草拟打招呼语"，每次投递需人在控制台点确认。风险最低，但失去"挂机"价值。
  - B2：v1 先只做只读 + 草拟（监听 HR 消息、AI 草拟回复），不自动投递；自动投递 v2 再开。最稳但交付价值缩水。
- 风险预警：封号后简历/沟通记录受损，求职进度受影响。建议用户可用小号或至少接受"被风控后暂停"的兜底。
- 置信度：70%
- 归入置顶原因：纯用户风险决策，Agent 不应代决。

#### Q4. 自动投递策略：筛选条件与打招呼方式
- 问题描述："投递简历"需明确：a) 投哪些职位（关键词/城市/薪资/经验/公司规模过滤）；b) Boss直聘的"投递"实为"点击沟通 + 发送打招呼消息"，打招呼语用固定模板还是 AI 按职位个性化生成；c) 每日投递上限。
- 建议方案：v1 实现**规则筛选 + AI 个性化打招呼**：配置搜索关键词（多组）、城市、薪资范围、经验要求、公司规模白/黑名单 → 逐职位抓取 JD → AI 结合简历生成个性化打招呼语（可叠加"AI 匹配度评估，低于阈值跳过"开关）→ 每日上限可配置（默认 30）。
- 备选方案：
  - B1：固定模板打招呼语（不用 AI 生成）。速度快、零 token 成本，但回复率通常更低。
  - B2：不做 AI 匹配评估，规则筛选通过即投。投得多但可能投进不合适岗位。
- 风险预警：AI 匹配评估会消耗 token（每个职位一次调用）；筛选条件过严会导致投递量不足。
- 置信度：75%
- 归入置顶原因：求职策略因人而异（期望薪资/城市/方向等求职目标——简历中已有，具体值已按 S2 脱敏；策略细节需用户确认），投错/投滥直接损失机会成本。

#### Q5. 自动回复 HR 的行为边界
- 问题描述：HR 主动发消息后，AI 是全自动回复，还是草拟后等用户确认再发？全自动省力，但 AI 答错关键问题（面试时间、薪资期望、到岗时间）会直接损失面试机会。
- 建议方案：**默认人工确认模式 + 可配置的全自动模式**。AI 草拟回复 → 控制台"待发箱"一键确认/编辑/跳过；另提供全自动开关（可按场景细分为：寒暄/感谢类自动发，涉及薪资/时间/面试的关键消息必须人工确认）。
- 备选方案：
  - B1：全自动回复一切消息。零人工，但关键问题答错风险高。
  - B2：全部消息一律人工确认。最稳，但用户不在线时 HR 得不到及时回复（Boss直聘回复速度影响推荐权重）。
- 风险预警：全自动模式下 AI 幻觉（编造经历、答应不存在的条件）无法拦截，需在 system prompt 中严格约束（只依据简历事实作答）。
- 置信度：80%
- 归入置顶原因：直接关系求职结果质量的风险决策。

#### Q6. AI 提供商与默认模型
- 问题描述："可以配置 AI"未指定提供商与默认模型。架构上建议统一走 OpenAI 兼容协议（base_url/api_key/model 全可配），但需确认用户实际持有的 API Key 作为默认配置与联调对象。
- 建议方案：**OpenAI 兼容协议统一接入**（配置文件含 base_url、api_key、model、temperature），DeepSeek/通义/Kimi/GLM/OpenAI 均可直接切换；默认按用户拥有的 Key 配置一家。
- 备选方案：仅接某一家官方 SDK（如 openai-sdk 指向 DeepSeek）。灵活度低，不推荐。
- 风险预警：无（协议是事实标准）。唯一阻塞点是用户没有任一家的 API Key 时无法联调，需提前告知。
- 置信度：90%
- 归入置顶原因：置信度虽高，但"用户实际有哪家 Key"是事实性信息，Agent 无从得知，必须问。

#### Q8. 通知渠道实现方式：HTTP 推送服务 / 本机微信-QQ 客户端自动化

- 建议方案：**HTTP 推送服务渠道（多渠道可配置 + 按事件路由）**：Server酱 / PushPlus / WxPusher（消息经微信服务号推送，手机微信可收）+ 企业微信群机器人 webhook + 邮件（SMTP）。支持按事件类型路由（如：登录失效/有面试/有 offer → 立即推送全渠道；例行统计 → 仅控制台）与免打扰时段。零即时通信账号风险、不受客户端版本更新影响。

### v2 自决区

#### Q9. 单会话自动回复计数规则
- 自决方案：每会话"自动发送消息数"计数**含打招呼语**（打招呼即计 1 次），达到上限（默认 2，可配 0-N）后该会话停止一切自动发送、转入待发箱全人工模式，并触发一次通知提醒用户接管。
- 自决理由：用户已给默认值 2，仅计数口径属实现细节；"含打招呼"口径更保守，与 Q3 风险偏好一致。
- 风险预警：无重大风险（v6 补注，历史条目格式补全；现行计数口径见 v6 §二对照表）。
- 置信度：90%
