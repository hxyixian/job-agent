## 1. 浏览器被拦截问题

### 1.1 现有实验能说明什么、不能说明什么

问题清单 v9-Q18 的结论是"驱逐是概率性的""与浏览器指纹无关""指向检测 CDP 控制通道"（置信度约 70%）。对照实验记录和 `private/survey/` 的元数据逐条复核：

| Q18 的判断 | 复核结果 |
|------------|----------|
| ④⑤ 形态相同、结果相反 → 驱逐是概率性的 | **不成立。** ④⑤ 至少有三个变量不同：<br>① 页面：④ 是未登录状态下的首页和搜索页；⑤ 停在扫码登录页，登录页通常是防护最严的页面。<br>② 时间顺序：profile 时间戳显示，5 组实验集中在 12:28–12:53 这 25 分钟里，在同一台机器、同一 IP 上进行；⑤ 是在 ④ 结束后几分钟内、用同一个 profile 开始的。设备或 IP 的风险评分可能是在这个过程中累积起来的。<br>③ 每种形态只测了 1 次。<br>这三种解释都和数据相符，现有数据区分不了。 |
| 与浏览器指纹无关 | **和数据矛盾。** ① 内置 Chromium（`browser_profile` 版本 156.0.8078.4，Chrome for Testing）几秒内被驱逐；④ 本机 Chrome（`probe_profile` 版本 156.0.8078.80）5 分钟没有被驱逐。浏览器二进制和启动参数至少在一定程度上有影响。 |
| 检测的是 CDP 控制通道本身 | **合理，但未验证。** 支持的线索：<br>• 公开讨论中常见一种现象：普通 Chrome 打开开发者工具（F12）后，Boss直聘 页面会跳到 about:blank，说明站点有反调试脚本；<br>• 开发者工具和 Playwright 用的都是 DevTools 协议，而 Playwright 连接后始终启用协议里的 Runtime 部分，可能触发同一套判断。<br>这只是推测，可以用实验 X0b 零成本验证。 |
| ②③ 进程死亡是本机硬件异常所致 | **判断合理，但应当记为"无效样本"，而不是"已排除"。** ②③（普通 Chrome 开调试端口，再 attach 上去）恰好是最能单独检验"纯 CDP 连接会不会被检测"的实验，却没有产出有效数据。<br>另外，事件 ID 里 LiveKernelEvent 141 通常对应显卡超时，BlueScreen 9F 通常对应驱动电源状态故障。这台机器要求每天无人值守运行 6 小时，这本身就是稳定性风险，建议先检查显卡驱动。 |
| 缺少对照组 | 所有实验结束后，**没有**再测"不用任何自动化的普通 Chrome，在这台机器和这个 IP 上还会不会被驱逐"。所以目前分不清是"自动化被检测"还是"设备/IP 已经被标记"。 |
| 证据留存 | Q18 写着"原始数据存 `private/survey/`"，但该目录下只有 3 个浏览器 profile 和 3 个脚本：`output/` 不存在，`manual/` 是空的，没有日志也没有截图。实验记录表是唯一的证据。 |

**有一点是好消息**：⑤ 中扫码没有完成，账号**大概率还没有**在自动化浏览器里登录过，账号层面应该还是干净的。目前的风险主要在设备和 IP 层面。这也是为什么后续实验要先做对照组（X0）。

### 1.2 实验过程本身的问题（产品代码和后续实验都要避免）

1. **被驱逐后立即重新导航**：
   - `probe.py` 每 5 秒检查一次，发现 about:blank 就重新打开首页；
   - `survey.py` 每次导航最多重试 3 次，等待扫码期间还**每 8 秒刷新一次页面**。这会让二维码失效，行为也非常像机器人。

   这些正是 R3"不盲目重试"所禁止的做法，很可能加速了评分累积。`probe2.py` 已经改成等待登录期间不刷新，方向是对的。
2. **抹除 `navigator.webdriver` 的注入脚本反而是一个破绽**：
   - 加上 `--disable-blink-features=AutomationControlled` 之后，真实 Chrome 的 `navigator.webdriver` 本来就是 `false`；
   - 注入脚本把它改成 `undefined`，并在 navigator 实例上新增了一个自有属性，这在真实浏览器里不会出现，反而容易被识别出来。
   - 设计文档 §5.3 继承了这个脚本，应当删除（G4）。
3. **25 分钟内连续 5 组实验**：前一组可能影响后一组的结果，见 1.1。

### 1.3 方案 A 的三个问题

1. **最大的风险被放到了最后。** 按 §14 的安排，S4b 浏览器会话层、S6 ZhipinAdapter（选择器、页面流程）都要在不知道"读页面能不能成功"的情况下开发完，到 TEST3 才第一次验证。如果失败，S4b/S6 要整体返工，需求范围也可能要重议，而且发生在项目末尾。
   另一方面，S1–S3（工程骨架、核心逻辑、AI 与通知）和浏览器完全无关。现在就做可行性实验，并不会拖慢进度。
2. **S2 DrissionPage 不是独立的后备。** Q18 自己写了"Playwright/Puppeteer/DrissionPage 底层同为 CDP"：
   - 如果根因是 CDP 通道，S2 会以同样的方式失败；
   - 如果根因是 Playwright 特有的痕迹，那么直接用"在协议层修补了这些痕迹、API 和 Playwright 兼容"的驱动更有针对性，架构完全不用改（见 1.5 的 S1b）。
3. **S3 键鼠模拟放不进 `BrowserSession` 接口。**
   - §5.3 定义的 `BrowserSession` 提供的是 Playwright 风格的页面操作（goto、wait_for、click、query 等）。键鼠模拟加视觉识别拿不到页面元素，无法实现 `query`，所以"切换策略不改上层"的说法对 S3 不成立。
   - S3 还和 NFR7"仅浏览器经 Playwright 操控；不操控其他本机软件"冲突，而且运行期间你没法正常使用这台电脑。
   - 它实际上是另一个 SiteAdapter 加一套视觉识别技术栈，接近重新立项。

### 1.4 建议：受控可行性实验（替代"推迟到 TEST3"）

**前置条件**

- 距上次实验（2026-11-06 12:53）≥ 24 小时；
- 先检查显卡驱动，或在 Windows"可靠性监视器"里确认最近没有新的硬件错误。否则浏览器进程死亡这类结果无法判读；
- 使用日常的家庭网络，不开 VPN，和正式运行的环境一致。

**通用规则**

- 每次实验只改一个变量；每天最多做 2 次。

- 全程只读：不点"立即沟通"，不输入文字，不发送任何内容。
- 每次实验把完整的控制台输出和每次 URL 变化（带时间戳）保存到 `private/survey/logs/`；实验结论写进问题清单 v10，并注明对应的日志文件。

### 1.5 后备路线重排（M2）

|------|------|--------|--------|----------|
| 1 | **S1a**：Playwright + 真实 Chrome + 登录在自动化之外 + 去掉注入脚本 | 当前设计减去已知破绽 | CDP 连接仍然存在 | 无 |

## 2. 设计文档修改项（G1–G13）

### G1.（高）频率计数漏算试运行和 `unknown`，试运行没有频率上限

- **位置**：§6 L243 `send_intents.state`、L255 限额查询、§7 L270。
- **问题**：
  1. §7 第 7 步写 `send_intents(SKIPPED_DRYRUN)`，但 `state` 的取值只有 `pending/sent/failed/unknown`，没有这一项；
  2. 限额查询只统计 `state IN (sent, pending)`，所以试运行的拟发送**不计入**上限，违反了 FR3.9 的频率规则；
  3. `unknown`（崩溃后结果未知的发送）也没计入。重启后这些发送被当作没发生，可能突破上限；
  4. `dry_run=当前模式` 意味着同一天里关闭试运行后，正式运行的计数从 0 开始，当天的实际暴露被重复使用。
- **建议**：
  - `state` 增加 `skipped_dryrun`；
  - 限额查询改为 `state IN (pending, sent, unknown, skipped_dryrun)`，**不按模式过滤**。限额衡量的是账号暴露，和是否试运行无关；
  - 去重名单、统计、会话计数仍然过滤 `dry_run=1`（N2 不变）。
- **验收用例**：试运行达到每小时 25 次后停止；同一天切到正式运行后，额度接着累计，不从 0 开始。

### G2.（高）没有处理这次实际观察到的拦截形态

- **位置**：§5.2 `RiskSignal`、§5.3 浏览器消失处理（L231）。
- **问题**：
  - 这次观察到的拦截表现是"页面被强制跳到 about:blank"，但 `RiskSignal` 里没有对应的信号；
  - §5.3 规定 `TargetClosedError` 后自动重新拉起浏览器，没有次数限制。如果浏览器是因为被检测而关闭，自动重建就是在盲目重试。
- **建议**：
  - 新增 `RiskSignal.EVICTED`：页面 URL 变成 about:blank，或跳转到不是我方发起的非站点域名 → 按风控熔断处理（暂停全部任务 + 高级告警），**禁止自动重新导航**；
  - 浏览器重建最多 1 次 / 小时；如果关闭前出现过 EVICTED，不重建，直接暂停等你处理；
  - 告警表 §11 的 high 级别加入"页面被驱逐"。

### G3.（高）页面浏览量没有上限

- **问题**：现有三级频率控制只限制"发送"，不限制"看"。
  - 假设 AI 评估通过率是 20%，每小时 25 次投递意味着每小时要打开约 125 个职位详情；
  - 8–20 秒的间隔，每小时最多允许约 260 次操作。

  正常求职者不会连续 6 小时、每小时看 100 多个 JD。这次被拦截的根因很可能包含行为评分，所以浏览量是主要的暴露来源。
- **建议**：
  - 新增 `browse_limits`：详情页每小时、每天的上限，搜索翻页每小时的上限。试运行和正式运行都适用；
  - 默认值由 X4 实验校准，在那之前先用一个保守值（如详情页 40/小时、200/天）；
  - 用户可见的影响要写清楚：按 200/天、通过率 20% 计算，每天实际最多投递约 40 次，每日上限 100 在这种情况下达不到。这是"安全优先于投递量"的取舍，配置页应当提示。

### G4.（中）浏览器层的抽象边界和启动参数

- `BrowserSession` 只给同属 CDP 的驱动用（S1a/S1b，二者 API 兼容）。扩展、键鼠这类路线作为独立的 SiteAdapter 注册，不要放进 `BrowserSession` 策略，并删掉 S2/S3 的占位（1.3、1.5）。
- §5.3 删除 `navigator.webdriver` 注入脚本（1.2 第 2 条）。最终的启动参数以 X2/X3 实验通过的形态为准。
- `channel="chrome"` 用的是本机 Chrome，它每 4 周左右自动升级，不受项目控制。启动时把 Chrome 版本记进日志；升级后第一次运行如果出现异常，可以快速定位原因。

### G5.（中）新增"登录模式"（配合 M3）

- `POST /browser/login-mode`：用普通方式启动 `chrome.exe --user-data-dir=<.browser_profile>`，不带调试端口或管道；你登录完成并关闭窗口后，引擎才可以启动。
- 同一个 profile 不能被两个 Chrome 进程同时打开。登录窗口打开期间，引擎启动应当被拒绝，并提示"请先关闭登录窗口"。
- FR1.3 登录失效后的恢复流程也走这个模式。

### G6.（中）`is_ours_auto` 不应由适配器提供

- **位置**：§5.1 L184、§8.1 L302、§13 L418。
- **问题**：平台不会标记哪条消息是本软件发的，适配器无从得知。B3 的人工接管检测和 §13 的对账，都依赖这个字段。
- **建议**：
  - 适配器只返回原始消息；`is_ours_auto` 由核心层计算：把我方消息和 `send_intents` 按内容摘要（`payload_digest`）加时间窗口（如 ±10 分钟）匹配；
  - 写明匹配规则，以及匹配不上时怎么处理（按人工消息处理，即转人工，这是保守的做法）。

### G7.（中）FR4.3 的标注工具在设计里没有

- 需求 R8 已经把"愿投/不愿投"标注和导出/导入写进 FR4.3 正文，L1 的关闭也依赖它，但设计文档的表、API、页面里都没有。
- **建议**：
  - `evaluations` 增加 `user_label`（want / not_want / null）；
  - 增加 `GET /evaluations/export`、`POST /evaluations/labels/import`；
  - 页面放在"投递记录与看板"下。

### G8.（中）跨站防护需要写明不启用 CORS

- §10.1 用自定义请求头防跨站请求。这只有在浏览器的跨域预检失败时才有效：一旦有人加了 CORS 中间件并放开来源，这层防护就失效了。
- **建议**：明确"不注册 CORSMiddleware，跨域预检一律拒绝"；可以再加一道 `Origin` 头校验。加入 S1 的验收项。

### G9.（低）"预置组 + 自定义组"的结构没有真正建模

- §4 的 `exclude_groups` 是一组布尔值，`exclude_keywords` 是一个空对象，体现不出 FR3.2 要求的结构。
- **建议**：改为一个组列表，如 `exclude_groups: [{id, kind: preset|custom, enabled, keywords, scope}]`。v1 只加载 `kind=preset` 的组。

### G10.（低）放量期的计日口径和 N1 的决策不一致

- §13 写的是"有投递动作的运行日才减 1"，N1 的决策是"3 个运行日"。设计的口径更合理（当天被平台限额拦住就不算），但要在问题清单里记一条自决，并同步到 FR3.9。

### G11.（低）运行时段内防止系统休眠

- B18 只处理休眠唤醒之后的恢复，更好的做法是运行时段内不让系统休眠：调用 `SetThreadExecutionState(ES_SYSTEM_REQUIRED)`，时段结束后释放。结合 1.1 提到的驱动电源状态故障，这一点在这台机器上尤其有用。

### G12.（低）B0 假设清单与 S6 的启动条件

- `private/survey/manual/` 目前是空的，B0 的 6 项事实都还没确认。§7 和 §8 隐含了几项假设，比如 `send_greeting` 发的是我方模板，平台不会自动发预设招呼语；索要简历是一张卡片。
- **建议**：
  - 在设计文档里单列"待验证假设"表：每项写明假设内容、影响哪个模块、被推翻后改哪里；
  - 把"手动素材已采集、假设已核对"写成 S6 的开工条件。

### G13.（低）Stage 安排配合可行性实验

- §14 增加一个"可行性实验"小节：X0–X4 和 S1–S3 并行；S4b（浏览器会话层）在实验定型后开工；S4 的其他 SubStage 不受影响，照常进行。
