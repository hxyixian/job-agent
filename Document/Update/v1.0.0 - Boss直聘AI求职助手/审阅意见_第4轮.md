## 0. 结论

### 0.1 浏览器路线：同意采用 S1b（Patchright）

这个工程决策是对的：S1b 在和产品相同的条件下（真实 Chrome、已登录、只读、产品节奏）连续运行 45 分钟没有被拦截，而且全程没有任何发送操作。Patchright 的情况已在本地核实（版本 1.64.4，许可证 Apache-2.0，基于 Playwright 1.64.1）。

但有两点要修正：

1. **归因说得过头了。** "S1a 与 S1b 唯一的差异是 Patchright 补丁"不成立。两次实验同时还换了 profile、换了登录状态、换了时间（V1）。这不影响采用 S1b，但文档里的因果表述要改。
2. **"定型"的依据比产品的实际负载小一个数量级。** 实验验证过的是：45 分钟、5 个不同位置的职位卡、详情间隔 41–53 秒，而且不检查页面内容。产品要求的是：每天 6 小时、每天最多 200 个详情、操作间隔 8–20 秒。所以第二轮 X4 必须用和产品完全一致的形态，并检查页面内容（V3、V4）；产品节奏也不能快于验证过的节奏（H2）。

### 0.2 阶段二门禁：暂不通过

修订后可以通过，不需要大改设计。设计主体、G1–G13 的落实情况、开发文档的 Stage 拆分都已达标。但有 6 项必须先修，否则 SubAgent 拿到的是互相矛盾的指令，或者没法并行写代码：

### V2.（中）X5 的结论不成立，但它揭示了一种新的拦截形态

- **结论为什么不成立**：
  - `_security_check=1` 在脚本附着的第一秒（14:47:07）就已经出现在 URL 里了。而几分钟前（14:4x）你刚在一个新 profile 上扫码登录，"新设备登录触发安全验证"同样是合理的解释；
  - `probe5.py` 只记录了异常的类型名（`Error`），没有记录异常信息，弹回首页的原因无从判断；
  - 问题清单 L553 的正文（"检测 CDP 附着本身"）和后注（"页面导航行为触发干预"）给出了两种互相矛盾的解释。
- **建议**：X5 标记为"不确定样本"。
- **对产品有价值的事实**：存在一种**在 zhipin.com 域名内**的拦截形态——URL 带 `_security_check` 参数，或者导航被弹回首页。实验脚本只判断"变成 about:blank 或离开 zhipin.com"，识别不了这种形态，设计 G2 的 EVICTED 也识别不了。见 H1。

### V3.（高）实验的"成功"判据太弱，"10 个详情"说多了

- `probe3.py` 判断是否成功只看 URL：只要没有变成 about:blank 或离开 zhipin.com，就算通过。以下情况它都会判为通过：
  - zhipin.com 域内的安全验证页；
  - 页面上弹出的验证码浮层；
  - 页面空白，内容没加载出来。
- X4 的"详情" URL 统一是 `/web/geek/jobs?query=python&city=101020100`，不带岗位 ID。脚本点击的是 `nth(i % 5)`，也就是**最多 5 个不同位置的卡片，每个点了两次**。职位描述到底有没有加载出来，没有任何记录。
- **后果**：S6 依赖"能读到职位描述正文"，而这一点还没有被证实。
- **建议**：第二轮 X4 在每个关键节点记录以下内容（只记数值，不存页面原文，可以入私有日志）：
  - 页面标题；
  - 职位卡数量；
  - 职位描述正文长度；
  - 详情面板里的岗位 ID；
  - URL 中是否出现 `_security_check`、`verify` 等字样；
  - 页面上是否出现"安全验证""环境异常"等文字。

  这些内容就是 B0 素材的一部分（见 W4）。

## 2. 设计补充项

### H1.（高）识别安全验证页、导航被弹回和页面内容异常

- **新增风险信号**：给 `RiskSignal` 加 `SECURITY_CHECK`，满足下列任一条件即触发：
  - URL 含 `_security_check`，或含验证类路径；
  - 页面上出现"安全验证""环境异常""验证码"等文字；
  - `goto(目标页)` 后实际停留的页面不是目标页（比如被弹回首页），连续出现 2 次。

  触发后按风控熔断处理：暂停全部任务 + 高级告警，禁止重试导航。
- **内容级健康检查**：页面加载了，但预期内容不在（比如搜索页一张职位卡都没有、详情页没有职位描述正文），计入 `AdapterBrokenError` 的连续失败次数（B7）。
- **同步修改**：
  - 设计 §5.2 / §5.3；
  - 开发文档 S6a 的 `detect_risk()`；
  - 开发文档 S4a 的 Mock 注入能力；
  - 验收文档新增一项（Y2）。

### H2.（高）节奏下限与浏览放量（产品节奏不能快于验证过的节奏）

1. **按请求类型设置最小间隔**。这是在 8–20 秒操作延时之外另加的约束，初始值为：
   - 打开职位详情 ≥ 30 秒（X4 实测间隔 41–53 秒）；
   - 加载搜索列表 ≥ 30 秒，包括打开搜索页、翻页、滚动加载更多（依据 boss-agent-cli 的 code 37 数据）。

   新增配置 `delivery.min_interval_s: { detail: 30, search: 30 }`，后续由试运行数据校准。

   这比小时上限更重要：小时上限控制的是总量，而 code 37 数据说明，**短时间内的突发请求**才是主要触发因素。
2. **试运行期间逐步放开浏览量**：
   - 第 1 个试运行日，详情上限 15 次/小时、60 次/天；
   - 每过一个没有风控信号的试运行日，上限翻倍，直到达到配置值；
   - 出现任何风控信号，回到第 1 档，并转你决策。

   这把"可行性验证"延续到了试运行阶段，补上 V5 说的差距。写进 FR3.9 和设计 §13。
3. **风控文字信号**：页面或接口出现"环境异常"类提示（code 37 在浏览器里的表现形式待第二轮 X4 观察）→ 归入 H1 的 `SECURITY_CHECK`。

### H3.（高）"半自动回退"没有定义（见 M5）

- **现状**：设计 §13 L445 规定"放量期第 1 天出现 EVICTED 或风控信号 → 直接回退半自动模式"；开发文档 S2d 也会发出 `fallback_semi_auto` 事件。
- **问题**：
  - 全文没有定义半自动模式：没有配置项，没说哪些动作改为人工、用户在哪里发送、发送后系统怎么识别；
  - 验收文档 §1 把半自动列为"不覆盖"，但按设计，它在 v1 里是会被自动触发的。
- **一个具体的冲突**：在半自动模式下，用户手动发出 AI 写的草稿后，B3 的人工接管检测会把这条消息判为"人工消息"，导致**每个会话都被标记为人工接管**，会话计数也乱掉。
- **二选一**：
  - **a（推荐）**：v1 不做自动回退。放量期出现风控信号 → 暂停全部任务 + 高级告警 + 转你决策（和 M2"每升一级由你确认"一致）。半自动等真正需要时，再作为 v1.x 立项。删掉 S2d 的 `fallback_semi_auto`。
  - **b**：v1 实现半自动，需要补充以下内容：
    - 配置 `send_mode: auto|manual`；
    - manual 模式下，所有 `send_*` 一律进待发箱，提供"复制草稿"和"标记已发送"操作；
    - 接管检测增加一条规则：我方消息和待发箱草稿按摘要匹配，匹配上的算"Agent 草拟、用户发送"，不判为接管；
    - 因风控触发回退时，**浏览也要暂停**，等你恢复；
    - 验收文档增加对应的验收项。

### H4.（中）可选：会话页常驻一个标签页

- 每次轮询都打开会话页，会增加导航次数。可以考虑让会话页常驻一个标签页，搜索和详情在另一个标签页里进行，轮询时只读 DOM，不导航。这和真实用户的使用方式一致，单执行者模型也照样适用（跨标签页依次操作）。
- 是否采用由 MainAgent 自决，在问题清单里记一条。

### H5.（低）清理实验用的 profile

- `private/survey/` 下有 4 个浏览器 profile，其中 attach_profile 里有真实账号的登录态。第二轮 X4 完成后，建议删除不再使用的 profile。产品只使用按 M3 流程新建的 `.browser_profile`。
